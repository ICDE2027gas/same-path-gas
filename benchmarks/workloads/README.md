# Workloads and state inputs

`uniswap/` contains the recorded 197 estimation positions: 9 ERC20 positions (`E`, 7 cases) and 188 Pair positions (`A`, 19 cases). The tests come from Uniswap V2 Core commit `4dd59067c76dea4a0e8e4bfdda41877a6b16dedc`, also published as `@uniswap/v2-core@1.0.1`. Contract artifacts use Solidity `0.5.16+commit.9c3226ce`, Istanbul and optimizer 999999. The service executes them under the recorded Osaka configuration in the context files.

The Pair workload reruns fixture construction for each case with the declared `uniform-auto-gas-v1` wallet adaptation. Its 188 estimates include 57 creations and 11 expected reverts. ERC20 has 2 expected reverts. `population.json` records every position in original RPC order, its original request/response, the full resolved block and the request with its canonical block-hash selector. Position counts describe distinct captured workflow positions, which benchmark passes repeat.

`ORIGINS.json` binds each portable input to the byte count and SHA256 of its original captured file. The export keeps every request, response, header, configuration, position and selector equal to its recorded source. It changes metadata/path bindings: the context's original-node directory is `states/E` or `states/A`, historical process-receipt paths are omitted, and the population points to the portable context identity. [rpc/run.py](rpc/run.py) copies these files to a fresh work directory, sets the absolute source-state path, recalculates the context identity and rebinds `population.context`. Request contents and block hashes stay fixed.

`STATES.expected.json` gives the exact data-only file inventory for each source database, preserving the original Geth instance name below `states/E/` and `states/A/`. It includes `chaindata` and `triedb` and excludes the node identity key, peer database and blob-pool files. The recorded data-only totals are 135,247 bytes/39 files for E and 2,139,563 bytes/41 files for A. After file checksums are verified, the RPC server checks every canonical header and root in a fresh writable copy and opens every historical state before declaring readiness. It also verifies that the context stays fixed across the request window.

`historical116/FILES.expected.json` identifies the 116-input historical corpus. The same 19 Pair cases use Ganache fixture reuse, producing 4 fixture sends and 112 body sends, with 11 expected reverts. These inputs include complete captured prestates, messages and Istanbul contexts, with payloads in the optional input data attachment. Fixture reuse produces a different population from the 188-position fresh workflow. Rebuilding the capture from public tests produces new timestamps and chain context, so reproducing the recorded inputs requires that attachment. [historical116/README.md](historical116/README.md) describes the historical runtime patch and whole-corpus qualification/measurement runner.

`controlled/` contains the author-written bounded ledger/permit contracts, the unchanged 27-instance schedule and five executed mixtures, the original public ERC20 artifact and a compiler version/hash binding. `coverage/` provides the additive native fixture and a process runner. See [coverage/README.md](coverage/README.md) for compilation, qualification and one complete measured-process example. `rpc/` contains portable service/load modules for fixed-state service measurements, with the orchestration interface described in [rpc/README.md](rpc/README.md).

The recorded main and serial P/S/C measurements use the earlier accepted-service implementation. Recorded replay P/V/C measurements use the current implementation with the replay option. Controlled measurements use the current implementation plus the native coverage fixture. Historical three-method measurements use the earlier historical checker/estimator runtime identified by `historical116/SOURCE_VARIANT.json`. Portability adapters have new source identities, while the paper measurements remain associated with their recorded versions and runs.
